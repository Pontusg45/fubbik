# fubbik

This file provides context about the project for AI assistants.

> **New to this codebase?** Use the `fubbik-dev` skill (`agents/project/skills/fubbik-dev/`) — its frontend patterns and pitfalls still
> apply. Its backend patterns describe the retired TypeScript backend in `legacy/`, not the live Rust crates.

## Git Rules

- **Always ask before pushing.** Never run `git push` without explicit user confirmation.

## Project Overview

- **Ecosystem**: Rust (API server, CLI, MCP server) + TypeScript (web app, VS Code extension, generated API client)
- **Purpose**: Local-first knowledge framework for storing, navigating, and evolving structured knowledge about codebases. Designed for both
  humans (web UI, graph visualization) and machines (CLI, API, VS Code extension, MCP server).

## Tech Stack

- **Runtime**: one Rust binary, `fubbik` (`crates/fubbik`), for the server, CLI and MCP server; Vite for the web app; bun for a few
  `packages/db` scripts (`pnpm scan`)
- **Package Manager**: pnpm (TypeScript workspaces) + cargo (Rust workspace, `crates/*`)
- **Task runner**: `just` (`Justfile`); the root `package.json` scripts delegate to it or to turbo

### Frontend

- Framework: TanStack Router, as a client-rendered SPA built by Vite (`apps/web/src/main.tsx`; no SSR entry). The dev server (port 3001)
  proxies `/api` and `/docs` to the API (`API_PROXY_TARGET`, default `http://127.0.0.1:3000`)
- CSS: tailwind
- UI Library: shadcn-ui (built on @base-ui/react — uses `render` prop, NOT `asChild`)
- Graph: @xyflow/react (React Flow)
- API Client: the generated OpenAPI client in `packages/client` (`@fubbik/client`). `apps/web/src/utils/api.ts` builds it with
  `createClient`; its types come from `openapi.json` via `pnpm gen:api`. It keeps an Eden-shaped `{ data, error }` response, which is why
  helpers are still named `unwrapEden` (`apps/web/src/utils/eden.ts`). Eden treaty itself is no longer used.
- Validation: arktype, in the sign-in and sign-up forms (`apps/web/src/features/auth/`) and in `packages/env`

### Backend

- Framework: axum (`crates/fubbik-api`), with OpenAPI generated by utoipa (`fubbik openapi`)
- Database access: sqlx (`crates/fubbik-db`)
- Errors: `fubbik_core::error::AppError` (`AppResult<T>`), mapped to HTTP statuses by `ApiError` in `crates/fubbik-api/src/error.rs`
- Project config: optional `fubbik.toml` feature switches (`crates/fubbik-config`, see "Feature switches")
- The retired TypeScript backend lives in `legacy/` for reference and is not built or run

### Database

- Database: postgres (v18)
- Schema authority: the sqlx migrations embedded from `crates/fubbik-db/migrations/` (`sqlx::migrate!`), applied when the server or seed
  connects
- Drizzle: `packages/db` keeps a reference Drizzle schema for `pnpm db:studio` (Drizzle Studio); it does not own the schema
- Extensions: pgvector 0.8.2 (embeddings), pg_trgm (fuzzy text search), Apache AGE (graph projection). The compose image is built from
  `docker/postgres/Dockerfile`

### Authentication

- The web app uses the better-auth client (`better-auth/react`, `apps/web/src/lib/auth-client.ts`)
- The Rust server implements the better-auth-compatible endpoints (`/api/auth/sign-up/email`, `/api/auth/sign-in/email`,
  `/api/auth/sign-out`, `/api/auth/get-session`) and verifies better-auth session cookies, in `crates/fubbik-api/src/auth/`

### Additional Features

- Testing: `cargo test` for the Rust crates (`just rust-test`, `just rust-test-fast`), vitest and Playwright for the web app
- AI: Ollama only (`crates/fubbik-ai`), for enrichment, embeddings and the `/api/ai` routes
- Embeddings: Ollama (nomic-embed-text) for local vector embeddings
- Logging: `tracing` + `tracing-subscriber` (filter with `RUST_LOG`)
- Observability: tower-http request IDs (`x-request-id`) and HTTP trace spans
- MCP: Model Context Protocol server for AI agent integration (`crates/fubbik-mcp`, run by `fubbik mcp`)

## Core Concepts

### Chunks

The central entity — discrete units of knowledge (conventions, architecture decisions, runbooks, etc.). Each chunk has:

- `title`, `content`, `type` (note, document, reference, schema, checklist)
- `tags` (via normalized join table with tag types)
- `scope` (JSONB key-value metadata)
- `appliesTo` (glob patterns linking chunks to file areas, via `chunk_applies_to` table)
- `fileReferences` (explicit bidirectional links to files/symbols, via `chunk_file_ref` table)
- `rationale`, `alternatives`, `consequences` (optional "why" decision context fields)
- `embedding` (768-dim vector for semantic search)
- `embeddingUpdatedAt` (tracks when embedding was last refreshed)
- AI-generated: `summary`, `aliases`, `notAbout`
- Health score (computed on-demand): freshness + completeness + richness + connectivity (0-100)
- Version history (append-only `chunk_version` table)

### Spaces & Workspaces

Chunks can be organized per-space. A space is identified by a `kind` discriminator (`code | wiki | notes | research`) and — for `code` kind spaces — a git remote URL (normalized) or local paths stored in the `space_code_metadata` side-table. Chunks can belong to multiple spaces or none (global).

- `space` table with `remoteUrl` (deprecated, now in `space_code_metadata`), `localPaths`, `name`, `kind`
- `space_code_metadata` side-table holding `remoteUrl`, `localPaths`, `defaultBranch` for `kind = 'code'` spaces
- `chunk_space` join table (many-to-many; formerly `chunk_codebase`)
- `workspace` table groups related spaces (e.g., frontend + backend + infra)
- `workspace_space` join table (formerly `workspace_codebase`)
- `feature_space` join table (formerly `feature_codebase`)
- `fubbik space current` detects the space for the current directory via git remote or local path
- Web UI has a space/workspace switcher in the nav

### Connections

Directed edges between chunks: `sourceId → targetId` with a `relation` type (related_to, part_of, depends_on, extends, references, supports,
contradicts, alternative_to). Connections are global (not space-scoped), enabling cross-project knowledge linking.

### Templates

Built-in + user-created chunk templates (Decision Record, API Reference, Meeting Notes, Checklist, Schema). Built-in templates are seeded
by the `core` seed module (`crates/fubbik-db/src/seed/core-catalog.json`) and are read-only. Users can duplicate and customize.

### Plans

The central unit of work. Each plan holds a description, linked requirements, structured analyze fields, and enriched tasks.

- `plan` table: `title`, `description` (markdown), `status` (`draft | analyzing | ready | in_progress | completed | archived` — labels only,
  ungated), `userId`, `spaceId`, `completedAt`
- `plan_requirement` — many-to-many link to existing `requirement` entities at the plan level
- `plan_analyze_item` — discriminated table holding five kinds: `chunk`, `file`, `risk`, `assumption`, `question`, each with kind-specific
  metadata (severity for risks, verified flag for assumptions, answer for questions, line range for files)
- `plan_task` — enriched tasks with `title`, `description`, `acceptanceCriteria` (JSONB string array), `status`
- `plan_task_chunk` — many-to-many linking tasks to multiple chunks with a relation (`context | created | modified`)
- `plan_task_dependency` — task dependencies; marking a task `done` auto-unblocks dependents in `blocked` state
- Web UI: `/plans` list, `/plans/new` (simple form), `/plans/:id` (sticky header + four sections: description, requirements, analyze, tasks)
- CLI: `fubbik plan create/list/show/status/add-task/task-done/link-requirement`

### Agent Coordination Boards

Plans are also durable coordination boards for root agents and sub-agents:

- `agent_run` stores reconnectable Plan-scoped identities and parent/child relationships
- `plan_task_claim` stores exclusive expiring leases over existing `plan_task` rows
- `coordination_entry` is an append-only journal for notes, questions, progress, decisions, handoffs, and artifacts
- Rust module: `crates/fubbik-api/src/coordination/` with persistence in `crates/fubbik-db/src/repo/coordination.rs`
- MCP tools: `join_board`, `read_board`, `claim_task`, `update_board_task`, `write_board_entry`, `ack_board`
- The board persists communication but does not wake agent processes; agents poll or rely on their host for live delivery

### Requirements

BDD-style requirements with Given/When/Then steps.

- `requirement` table with `title`, `description`, `steps` (JSONB array of `{keyword, text}`), `status` (passing/failing/untested),
  `priority` (must/should/could/wont)
- `requirement_chunk` join table linking requirements to chunks
- Plans link to requirements through `plan_requirement` for traceability; requirement status is set explicitly (API, CLI `fubbik req
  status`, MCP `update_requirement_status`)

### Behavioral Matrices

Grid-based specs of expected behavior. A `behavior_matrix` (`layer = invariant | contract`) holds `behavior_dimension` columns and
`behavior_rule` rows; their intersection is a `behavior_cell`. Cells carry evidence and code links; cell status is computed on-the-fly.

- `behavior_rule` documents a behavior with `title`, `description`, `category`, plus decision-context fields `rationale`, `alternatives`,
  `consequences`, and an explicit `counterexample` (what violating it looks like).
- `behavior_rule_version` — append-only history; the service snapshots the pre-edit rule on every update (auditable evolution).
- `behavior_cell_requirement` — links a cell to BDD requirements (proof of behavior).
- `behavior_cell_code` — links a cell to concrete code (`kind = file | symbol | test`, `ref`). Powers reverse lookup
  (`GET /api/matrices/behaviors-for-file?path=`) and surfaces "Behaviors governing this file" in the file-context output.
- `behavior_test_result` — recorded `pass`/`fail` outcomes that drive verification status from real runs.
- Cell status (computed in the matrix view): `violated` (a failing requirement or failing test), `verified` (passing test evidence),
  `specified` (has requirements), `unspecified` (gap). The view also returns per-cell `codeCount`/`passingTestCount`/`failingTestCount`.
- Behavior rules are projected into the AGE graph as `behavior_rule` vertices with `governs` edges to `code_file`/`code_symbol`
  (`spawn_behavior_sync` in `crates/fubbik-api/src/graph/sync.rs`, started by `fubbik serve` when `matrices` is enabled); toggled via the
  "Behavior" button in the graph view.
- Surfaces: web `/matrices` + `/matrices/:id` (editable grid, cell panel, rule history dialog), CLI `fubbik matrix …`, and MCP matrix tools.

### Chunk Health Scores

Per-chunk health scores (0-100) computed on-demand from:

- **Freshness** (0-25): days since last update
- **Completeness** (0-25): has rationale/alternatives/consequences
- **Richness** (0-25): content length + AI enrichment
- **Connectivity** (0-25): number of connections Exposed via chunk detail API response and shown as a badge on the detail page.

### Features (Knowledge Overlays)

Named entities that track field-level modifications to chunks. Each feature stores deltas — sparse JSONB objects containing only the changed
fields. Features have a priority (higher wins on same-field conflicts) and can be toggled on/off globally via the nav switcher.

- `feature` table: `name`, `description`, `priority` (unique per user), `status` (inactive/active/merged/archived), `color`, `userId`
- `feature_space` join table (optional space association; formerly `feature_codebase`)
- `chunk_feature_delta` table: one delta per chunk per feature, contains JSONB with changed content fields only (title, content, type,
  rationale, alternatives, consequences, summary)
- `user_active_feature` table: persists which features are active per user
- Resolution: active deltas are folded field-by-field in ascending priority, so the highest priority wins — applied at the service layer
  (e.g. `resolve_feature_overlays` in `crates/fubbik-api/src/context/service.rs`)
- Merge: permanently applies all deltas to base chunks (with version snapshots), sets feature status to `merged`
- Feature switcher in nav bar alongside space switcher
- `/features` management page with create, merge, archive, delete actions

### Staleness Detection

Proactive detection of chunks that may need attention:

- `chunk_staleness` table tracks flags with `reason` (file_changed, age, diverged_duplicate), `detail`, and dismiss/suppress state
- `staleness_scan` table tracks per-space last scanned git commit SHA for incremental scans
- Age-based detection: flags chunks not updated in 90+ days (configurable threshold)
- Flags are dismissable (soft-delete with timestamp) or permanently suppressible (for duplicate pairs)
- Surfaced across the UI: dashboard "Attention Needed" widget, nav badge on Dashboard link, amber banners on chunk detail pages

### Scope Schema Registry

Optional registry for chunk scope keys. The `scope_key` table defines expected keys with types (string, number, boolean, enum) and allowed
values. Used for UI autocomplete and optional validation. Scope remains free-form JSONB — the registry is opt-in.

## Architecture Patterns

### Backend: Repository -> Service -> Route

Crate layering, lowest first: `fubbik-core` and `fubbik-contracts` (no I/O) → `fubbik-db` and `fubbik-ai` → `fubbik-api` → `fubbik`
(the binary). `fubbik-cli` and `fubbik-mcp` talk to the API over HTTP and do not depend on `fubbik-db` or `fubbik-api`.

- **Repositories** (`crates/fubbik-db/src/repo/*.rs`): sqlx queries taking a `&PgPool`, returning `AppResult<T>`. Pure data access, no
  business logic.
- **Services** (`crates/fubbik-api/src/<domain>/service.rs`): Compose repository calls, add business logic, return
  `AppError::NotFound`/`Auth`/`Validation`/`Conflict`/`External`.
- **Routes** (`crates/fubbik-api/src/<domain>/routes.rs`): axum handlers annotated with `#[utoipa::path]`; each module exposes a
  `router()` merged in `fubbik_api::router` (`crates/fubbik-api/src/lib.rs`). Handlers take `State<AppState>` and the `CurrentUser`
  extractor (401 when unauthenticated) and return `ApiResult<Json<T>>`. Request/response types live in `dto.rs`.
- **Error mapping** (`crates/fubbik-api/src/error.rs`): `ApiError` wraps `AppError` and maps it to a status (Validation->400, Auth->401,
  NotFound->404, Conflict->409, UnsupportedMediaType->415, Database->500 or 503 on pool timeout, External->502). Database errors are logged
  and returned as a generic message.
- **Feature-gated groups**: `fubbik_api::router` mounts the plans, requirements, matrices, coordination, learning-paths, overlays and AI
  routers only when their `fubbik.toml` switch is on (see "Feature switches").

### Frontend: Feature-based Structure

- Route files in `apps/web/src/routes/`
- Feature components in `apps/web/src/features/` (e.g., `features/auth/`, `features/graph/`, `features/spaces/`, `features/plans/`,
  `features/chunks/`)
- Shared UI in `apps/web/src/components/ui/`
- Shared page components: `PageContainer`, `PageHeader`, `PageLoading`, `PageEmpty` in `components/ui/page.tsx`
- UI components use base-ui `render` prop pattern (NOT Radix `asChild`)
- `DropdownMenuSeparator` and `DropdownMenuLabel` use plain HTML elements (NOT base-ui primitives) to avoid Menu.Group context requirement

### VS Code Extension

- Standalone package at `apps/vscode/`, does NOT import from other fubbik packages
- Communicates with the fubbik API via HTTP (fetch-based)
- Bundled to CJS via esbuild
- Webview sidebar with type/tag/sort filtering, file-aware chunk surfacing
- Webview panels for chunk detail, chunk creation, chunk editing
- Status bar showing chunk count
- Commands: search, quick-add note, open graph/dashboard in browser

### Context Pipeline (Unified)

All context retrieval flows through a single pipeline in `crates/fubbik-api/src/context/`, with the pure pieces in `crates/fubbik-core`:

```
Input Source → Chunk Resolver → Enrichment (health, stale, features) → Scorer + Budgeter → Formatter → Output
```

- **Resolvers** (`context/resolvers.rs`): `resolve_for_plan`, `resolve_for_concept`, `resolve_for_files`. Each produces candidate chunk
  IDs only. The concept and files resolvers degrade a failing step to "no contribution" rather than failing the call.
- **Enrichment** (`enrich_chunks` in `context/service.rs`): Fetches full rows, connections, tags, stale flags, proposals, active feature
  overlays. Computes health scores (`fubbik_core::health::compute_health_score`).
- **Feature Overlays** (`resolve_feature_overlays` in `context/service.rs`): Applies active feature deltas to chunks in the enrichment
  pipeline. All context paths get overlays automatically. Only `title`, `content`, `type` and `rationale` are overlaid here.
- **Scoring** (`crates/fubbik-core/src/score.rs`): `score_chunk` combines health, type, rationale, connections, review status.
  `budget_chunks` greedily fills a token budget. Token estimation (`crates/fubbik-core/src/tokens.rs`) uses the **o200k_base** encoding
  via the `tiktoken-rs` crate, which embeds its BPE data at compile time, so there is no length-based fallback.
- **Formatting** (`crates/fubbik-core/src/format.rs`): Groups by section, adds `[health: N]`, `⚠ STALE`, `⚠ PENDING PROPOSAL`
  annotations.
- **Low-level retrieval** (`crates/fubbik-api/src/context_for_file/service.rs`): Five strategies — file-ref (+20 bonus), applies-to
  (+10), dependency (+3), semantic (+5, requires Ollama), connected (+2). First strategy to find a chunk wins; bonuses do not stack.
  Results scored and sorted by relevance.
- **CLAUDE.md generation** (`crates/fubbik-api/src/context_export/claude_md.rs`): Tag-based export with requirements and active plans.
  Supports `maxTokens` budget (default 32000).
- **Snapshots** (`context/snapshot.rs`): Frozen context persisted as JSONB. User-scoped (auth-checked on retrieval).

### MCP Server

- Located at `crates/fubbik-mcp/`; run by `fubbik mcp` (JSON-RPC over stdio). `fubbik mcp-tools` lists the tools (53 today)
- It is an HTTP client of the API (`src/api.rs`, `ApiClient`), not a database client. Server URL: `--url`, else `FUBBIK_SERVER_URL`, else
  the CLI's configured URL, else `http://localhost:3100`. `agents/mcp/claude-code.json` is a ready-made Claude Code config
- Core tools (chunks, context, snapshots, requirements, vocabulary, quick tasks) are defined in `src/lib.rs` (`tools()`); plan, matrix and
  coordination tools live in `src/tools/{plan,matrix,coordination}.rs`, each with `definitions()` and `handles(name)`
- Key tools: `get_context`, `get_context_for_task`, `create_plan`, `add_plan_task`, `create_requirements_batch`, `get_matrix_view`,
  `join_board`, `sync_claude_md`

## Feature switches

A fork can turn whole feature groups off with an optional, committed `fubbik.toml` (template: `fubbik.example.toml`; loader:
`crates/fubbik-config`). Personal settings (secrets, URLs, ports) stay in `.env`.

```toml
[features]
plans = true
requirements = true
matrices = true        # requires requirements
coordination = true    # requires plans
learning_paths = true
overlays = true
ai = true
```

- Every key defaults to on; a missing file, a missing `[features]` table, or a missing key all mean "on"
- `fubbik serve` reads `./fubbik.toml`, or the file named by `FUBBIK_CONFIG`
- Unknown keys and unknown sections are errors, as is enabling `matrices` without `requirements` or `coordination` without `plans`
- A disabled group's routes are not mounted, and its background jobs do not start (for example, behavior-graph sync with `matrices` off).
  The database schema is always complete; migrations never depend on the switches
- Core (chunks, connections, spaces, tags, search, context, graph, ...) has no switch
- `ai = false` unmounts only the `/api/ai` routes. Enrich, semantic search, check-similar and vocabulary suggest stay on; they already
  degrade without Ollama
- `GET /api/capabilities` (unauthenticated) returns `{ "features": [...] }` with the enabled keys. The web app reads it through
  `apps/web/src/features/nav/use-capabilities.ts` and hides nav entries for disabled groups

## API Endpoints

### Core

- `GET /api/health` — system health check
- `GET /api/health/knowledge` — knowledge health (orphan, stale, thin chunks, stale embeddings, file refs)
- `GET /api/stats` — aggregate stats
- `GET /api/capabilities` — enabled `fubbik.toml` feature groups (unauthenticated; see "Feature switches")

### Chunks

- `GET /api/chunks` — list (supports `spaceId`, `workspaceId`, `global`, `allSpaces`, `search`, `type`, `tags`, `tagMode=any|all`,
  `sort`, etc.)
- `POST /api/chunks` — create (with optional `spaceIds`, `rationale`, `alternatives`, `consequences`)
- `GET /api/chunks/:id` — detail (includes connections, spaces, appliesTo, fileReferences, healthScore)
- `PATCH /api/chunks/:id` — update (auto-re-enriches on title/content change)
- `DELETE /api/chunks/:id` — delete
- `GET /api/chunks/search/semantic` — embedding-based search
- `GET /api/chunks/search/federated` — cross-space search with space names
- `POST /api/chunks/check-similar` — duplicate detection (requires Ollama)
- `GET /api/chunks/export/context` — token-budgeted context export (supports `forPath` relevance boost)
- `GET /api/chunks/export/claude-md` — CLAUDE.md generation from tagged chunks (supports `maxTokens` budget)
- `POST /api/chunks/import-docs` — bulk import from markdown files with frontmatter parsing

### Chunk Sub-resources

- `GET/PUT /api/chunks/:id/applies-to` — glob pattern metadata
- `GET/PUT /api/chunks/:id/file-refs` — file reference links
- `GET /api/chunks/:id/history` — version history

### File References

- `GET /api/file-refs/lookup?path=<path>` — reverse lookup (which chunks reference this file)

### Spaces

- `GET /api/spaces` — list
- `POST /api/spaces` — create
- `GET /api/spaces/detect?remoteUrl=&localPath=` — detect space from git remote or path
- `PATCH /api/spaces/:id` — update
- `DELETE /api/spaces/:id` — delete

> The Rust server keeps one deprecated `/api/codebases` route, `GET /api/codebases/:id/generate-instructions` (alias of the space
> route). The rest of the old `/api/codebases` alias was not ported.

### Workspaces

- `GET /api/workspaces` — list workspaces
- `POST /api/workspaces` — create
- `GET /api/workspaces/:id` — detail with spaces
- `PATCH /api/workspaces/:id` — update
- `DELETE /api/workspaces/:id` — delete
- `POST /api/workspaces/:id/spaces` — add space
- `DELETE /api/workspaces/:id/spaces/:spaceId` — remove space

### Templates

- `GET /api/templates` — list (built-in + user's custom)
- `POST /api/templates` — create custom
- `PATCH /api/templates/:id` — update custom
- `DELETE /api/templates/:id` — delete custom (built-in protected)

### Plans

- `GET /api/plans` — list (filters: `spaceId`, `status`, `requirementId`, `includeArchived`)
- `POST /api/plans` — create (body: `title`, `description?`, `spaceId?`, `requirementIds?`, `tasks?`)
- `GET /api/plans/:id` — detail (plan + requirements + analyze grouped by kind + tasks with chunks + dependencies)
- `PATCH /api/plans/:id` — update title/description/status/spaceId
- `DELETE /api/plans/:id`
- `POST /api/plans/:id/requirements` / `DELETE /api/plans/:id/requirements/:requirementId` / `POST /api/plans/:id/requirements/reorder`
- `GET /api/plans/:id/analyze` / `POST /api/plans/:id/analyze` / `PATCH /api/plans/:id/analyze/:itemId` /
  `DELETE /api/plans/:id/analyze/:itemId` / `POST /api/plans/:id/analyze/reorder`
- `POST /api/plans/:id/tasks` / `PATCH /api/plans/:id/tasks/:taskId` / `DELETE /api/plans/:id/tasks/:taskId` /
  `POST /api/plans/:id/tasks/reorder`
- `POST /api/plans/:id/tasks/:taskId/chunks` / `DELETE /api/plans/:id/tasks/:taskId/chunks/:linkId`

### Requirements

- `GET /api/requirements` — list (supports filters: status, priority, spaceId, search)
- `GET /api/requirements/stats` — counts by status
- `POST /api/requirements` — create with BDD steps
- `GET /api/requirements/:id` — detail

## Seed Data

Run `pnpm seed` (= `cargo run --locked -p fubbik -- seed`) to populate the database with sample data. Seeding is native Rust
(`crates/fubbik-db/src/seed/`), built from modules with dependencies, selected by scenario:

- Every run first ensures the dev user (`dev@localhost`) exists, in one transaction with the selected modules
- `--scenario minimal`: `core` (built-in chunk types, relations, templates) and `self-documenting`
- `--scenario demo` (default) and `extended`: every module — `core`, `codebases` (the fubbik code space), `tags`, `chunks`, `connections`,
  `file-links`, `use-cases`, `requirements`, `plans`, `agent-coordination`, `documents`, `vocabulary`, `workspaces`, `collections`,
  `matrices`, `self-documenting`
- `--only <modules>` / `--skip <modules>` narrow the set (dependencies are pulled in; skipping a required one is an error);
  `--reset auto|none` controls clearing the selected modules first
- Fixture data lives in `crates/fubbik-db/src/seed/*-catalog.json`
- The seeded space's local path and remote URL come from `FUBBIK_SEED_SPACE_PATH` and `FUBBIK_SEED_REMOTE_URL`
- The seed does not call Ollama; run `fubbik enrich --all` afterwards for summaries, aliases and embeddings

## Ollama (Optional)

Required for chunk enrichment (summary, aliases, not_about generation), semantic search, and duplicate detection.

- `ollama pull nomic-embed-text` — embedding model
- `ollama pull llama3.2` — generation model for metadata
- `OLLAMA_URL` env var (default: `http://localhost:11434`)
- Without Ollama, all other features work normally
- Editing a chunk's title or content triggers a **full re-enrich**, not just an embedding
  refresh: `summary`, `aliases` and `not_about` are regenerated too, overwriting a
  hand-written summary. Fire-and-forget; failures are logged and never fail the request.
- Enrichment concurrency: 3 (for enrich-all), which also caps at 1000 chunks per sweep
- Ollama failures are handled four different ways, all matching the original TypeScript:
  `enrich` probes availability first and degrades to `null`; `GET /api/chunks/search/semantic`
  does not probe, so an unreachable Ollama surfaces as a 502; the `similar-to:` search
  clause degrades to an empty clause so one clause's outage cannot fail a whole query;
  and `suggest_vocabulary` is infallible — no probe, no error path, every failure mode
  collapses to `[]`.

## Environment Variables

Personal settings live in `.env` (see `docs/guide/getting-started/configuration/environment.md`); project feature switches live in
`fubbik.toml` (see "Feature switches").

- `PORT` — Server port for `fubbik serve` (default: `3100`; `just dev` / `pnpm dev` pass `--port 3000`)
- `HOST` — Bind address for `fubbik serve` (default: `127.0.0.1`)
- `CORS_ORIGIN` — Comma-separated allowed origins (default: `http://localhost:3001`)
- `DATABASE_URL` — PostgreSQL connection string (required by `serve` and `seed`)
- `BETTER_AUTH_SECRET` — Auth secret (min 32 chars); the Rust server uses it to verify session cookies
- `BETTER_AUTH_URL` — Auth server URL. Validated by `packages/env`; the Rust server does not read it (it accepts both the plain and the
  `__Secure-` session cookie names)
- `OLLAMA_URL` — Ollama server URL (default: `http://localhost:11434`)
- `STALENESS_SCAN_INTERVAL_HOURS` — Hours between automatic staleness scans (default: `24`, set to `0` to disable)
- `BEHAVIOR_GRAPH_SYNC_INTERVAL_HOURS` — Hours between behavior-rule projections into the AGE graph (default: `24`, set to `0` to
  disable). Not started when `matrices` is off.
- `NODE_ENV` / `FUBBIK_IMPLICIT_DEV_SESSION` — unless `NODE_ENV=production`, or whenever `FUBBIK_IMPLICIT_DEV_SESSION=true`, the server
  serves unauthenticated requests as the dev user (it logs a warning at startup). Set `NODE_ENV=production` to require real sessions
- `FUBBIK_CONFIG` — Path to `fubbik.toml` (default: `./fubbik.toml`)
- `FUBBIK_URL` — API URL for CLI commands; `FUBBIK_SERVER_URL` — API URL for `fubbik mcp`
- `FUBBIK_SEED_SPACE_PATH` / `FUBBIK_SEED_REMOTE_URL` — Local path / remote URL of the seeded code space (defaults: the current
  directory / its `origin` remote)
- `FUBBIK_WEB_ALLOWED_HOSTS` — Comma-separated extra hostnames for the Vite dev server's `server.allowedHosts`
